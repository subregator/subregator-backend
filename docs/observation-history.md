# Durable check history

BE-10 adds normalized observations beside listing history in the existing PostgreSQL database. The latest JSON caches remain disposable. No new service, dependency, source call, public-triggered collection or automatic retention deletion is introduced.

## Approval and publication

`SUBREGATOR_HISTORY_CHECKS` / `-history-checks` is an exact comma-separated allowlist, empty by default. Supported values are `prefix_overview`, `rpki`, `registration`, `rdap`, `spamhaus_drop`. Enable a check only after confirming its retention and public-history rights, including every authoritative RIR used by RDAP. Existing source-access review has not established these rights. This flag is an operator assertion of approval, not evidence of a grant. Removing a check immediately excludes its stored rows from public reads and stops new writes; it does not delete data. Network enablement and collection budgets remain separate.

IRR, AbuseIPDB and ZEN cannot be added to this allowlist, even when current collection is enabled. Their historical retention/publication is pending. No raw complaints or per-IP details are archived. AbuseIPDB currently supplies address summaries rather than stable individual report IDs; long-term complaint identity and rolling-window resolution are unsupported until source terms and a separately scoped report adapter are available. DROP retains source listing references in matches without merging distinct references.

Public REST `GET /api/v1/network/history?resource=1.1.1.0/24&limit=50` and MCP `network_history` with `filters={"resource":"1.1.1.0/24","limit":"50"}` read PostgreSQL only. Exact IPv4/IPv6 public prefixes must be known through a provider whose current policy permits full disclosure. Hidden, pending and Peaktera histories are excluded. No free-form IP/ASN lookup or enumeration endpoint is provided. `after_id` is an ascending ingestion-ID cursor; `next_cursor` is omitted at the end. Limits are 1–200; evidence is capped at 64 KiB per row. Current provider and check approval are reapplied to all pages, including removed listings. Existing request admission limits still apply.

## Observation and event semantics

Each immutable row retains check/source attribution, requested and actual scope, collection outcome, completeness, captured freshness, local observation time, source update time when supplied, expiry and a separate ingestion time. BGP query time and nested RPKI/registry source dates are also retained in normalized evidence. Missing source dates stay null. Raw response bodies, credentials and external diagnostics are not archived. Historical `freshness` describes capture time, not present validity.

Identity is SHA-256 over resource, check/source, observation time (attempt time for a failure), source update time, normalized envelope and evidence. Replaying the same observation with a later ingestion time is idempotent. Independent polls remain independent sightings. Event identity is the observation identity; numeric IDs provide pagination, not dates. An atomic transaction stores the row and its inferred event together under a database advisory lock. Failed/canceled writes leave no partial event; retry the same observation safely. Persistence failures increment the existing health counter. No archive failure is reported as a successful historical write; there is no durable upstream replay queue, so a database outage can lose an observation before the next poll.

Only successful, fresh, complete, known-scope observations can establish changes. The last complete observation of the same source/check/scope is compared with the new one. BGP origin sets, per-origin RPKI states, normalized registry records and DROP presence produce distinct events. Registry changes are observed registry facts, never owner/tenant transfers. Unknown/multiple registry scope and partial RPKI origins remain noncomparable gaps. Historical/proposed-ASN inspections are excluded. No event is inferred from a cache read.

Failures, malformed/truncated results, quota/auth errors, stale observations and incomplete snapshots are `gap` rows. A later complete comparable check may establish DROP absence; only that creates `delisted`. TTL expiry, cache eviction and missing rows never create delisting/resolution. A recovered comparison can span a gap, explicitly marked `gap=true`. `previous_seen` and `observed_at` bound the inferred change; the exact date between polls is unknown. `first_seen` and `last_seen` are earliest/latest recorded sightings of the same state, not continuous presence or source event dates. A first observation has unknown preceding coverage. Expired prior evidence marks a coverage gap. Late/reordered observations remain `out_of_order` and never rewrite previously emitted events or infer retroactive changes; simultaneous conflicting observations are also non-inferential. No completeness before tracking began is claimed.

## Migration, retention and operations

Opening the database applies additive schema version 2 in the existing migration transaction. `check_observations` and its indexes are added; existing listing history, imports, caches and reservations are preserved. There is no backfill from disposable caches or synthetic past observations. Old version-1 binaries reject version 2: use a pre-migration backup in a separate database for rollback, preserving the migrated database and its new history. Do not downgrade by deleting tables or history.

Retention is indefinite, with no scheduled purge, while the approved source agreement permits it. Confirm duration before enabling each check; if a finite duration or erasure requirement applies, keep that check disabled until compliant retention handling is implemented. Revoking publication does not itself erase records or backup copies. Monitor table/index/WAL sizes and provision capacity before enabling. For 1,000 prefixes at five-minute BGP+RPKI polling, two six-hour registry checks and daily DROP, budget about 585,000 observations/day. At 2–8 KiB per indexed row this is roughly 1.2–4.7 GB/day, before WAL, replicas and backup copies; large evidence can exceed that estimate. Collection remains bounded, but this archive is deliberately not a size-evicted cache. Enable only approved checks and measured capacity.

Use existing PostgreSQL `pg_dump`/`pg_restore` procedures for the entire database, including schema migrations and all history; test restore into an isolated database. Backups inherit source retention and access restrictions. Disabling publication in restored runtime configuration still applies to old rows. Never substitute a JSON cache/snapshot export for a database backup. Stand/production migration, capacity, backup scheduling, live-source compatibility and contractual approval are separate delivery checks.

## Local validation

Real-PostgreSQL synthetic fixtures cover v4/v6, restart, cache eviction, duplicate/replayed and reordered observations, failure-to-success recovery, conservative delisting, expiry gaps, scope isolation, atomic interrupted writes and keyset pagination. Collector tests use mocked HTTP responses; public REST/MCP tests use a loopback server and actual PostgreSQL, including hidden/pending/disabled policy changes. Container smoke uses a synthetic offer feed with external collection disabled. These are local tests, not live-provider or production evidence.
