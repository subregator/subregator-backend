# Private RPKI validation

RIPEstat remains the default. Setting `SUBREGATOR_ROUTINATOR_URL=http://routinator:8323` selects an existing private Routinator for current RPKI validation only. No public handler invokes collection. REST/MCP metric and offer-check shapes remain unchanged: valid, invalid (with per-origin invalid_asn or invalid_length), not_found, mixed and partial retain their meanings. Supplied VRPs are explanations from the validator, never a second local implementation of RPKI validation. At most four origins and 32 covering VRPs per origin are retained; omissions are explicit. Proposed-ASN results remain separate from observed BGP origins.

The official [HTTP API](https://routinator.docs.nlnetlabs.nl/en/stable/api-endpoints.html) returns prefix/ASN results and supporting VRPs. [Validity explanations](https://routinator.docs.nlnetlabs.nl/en/stable/validity-checker.html) distinguish ASN and maximum-length failures. The adapter accepts the pinned 0.15.3 response shape, including string ASN/max_length values, validates scope and rejects malformed, oversized or stale responses. `source` is Routinator, with a public documentation URL; the private service URL is not exposed. The historical RIPEstat cache remains separate and usable when the setting is cleared. Restored automatic reports also reject results from the other selected source.

`source_updated_at` is the validator's last completed validation run, not the upstream publication time of every ROA. The adapter requires all five RIR trust anchors to have VRPs and both that timestamp and the returned snapshot `generatedTime` to be no more than one hour old. Result expiration cannot exceed either deadline or the existing five-minute result TTL. The process also requires a successful validator status check within five minutes for cached/offer freshness. Known status/transport/normalization failures immediately remove that freshness; after restart it remains stale until a collector confirms health. Public reads remain local: an outage between status checks can be detected only at the next collector check or the five-minute health lease deadline. This is bounded last-known health, not continuous availability assurance. A recent run is not proof that every repository fetched successfully; Routinator rejects expired manifests/CRLs (`--stale reject`), and repository failures can reduce available coverage. Completeness remains scoped to supplied origins and VRPs, not global routing safety.

Private reads use two concurrent slots, an eight-second context deadline and a 1 MiB JSON limit. Status and validity requests use the existing HTTP instrumentation without acquiring external RPM. Parent cancellation interrupts both slot waits and HTTP reads. RIPEstat overview/network-info is still needed for observed origins and IP-to-prefix resolution. One cold observed-prefix RPKI check needs one external overview request plus one private status and up to four private validations; a fresh cached overview needs zero new external requests. An explicit public prefix plus proposed ASN needs no BGP lookup in local mode. Independent routing_status and other checks still spend external budget. The external limit stays at 120 requests/minute. Measure overview/routing consumption and queue freshness separately; replacing RPKI does not remove these dependencies.

## Runtime and data terms

[Official installation guidance](https://routinator.docs.nlnetlabs.nl/en/stable/installation.html) calls for at least 1 GB available memory, 4 GB disk and two million free inodes, with outbound HTTPS 443 and rsync 873 access. Initial synchronization can take minutes. `deploy/routinator/compose.yaml` pins the official multi-architecture image by digest, uses its unprivileged UID 1012, a persistent cache, a read-only root, two CPUs, 2 GiB memory and 256 processes. No host port or RTR listener is configured. Its private bridge is attached only to the validator and opted-in backend, and still permits the validator's required outbound downloads. Its HTTP healthcheck proves the status API is serving after initialization; backend timestamp/trust-anchor checks separately determine data usability. Watch memory, disk and inode growth; the memory limit is not a disk quota.

Routinator is BSD-3-Clause licensed; that software license does not replace RIR data terms. Since Routinator 0.12 the bundled ARIN TAL no longer needs an initialization acceptance flag. The [ARIN Relying Party Agreement](https://www.arin.net/resources/manage/rpki/rpa.pdf), dated 13 February 2023, section 5 permits informational reporting, research, summaries and statistics, while routing redistribution is separately constrained by section 9. Subregator provides informational observations, not an RTR feed or a routing availability guarantee. Other RIR repository/CPS terms continue to apply. This integration does not close existing source-policy gates or authorize new archival use. `SUBREGATOR_HISTORY_CHECKS` and `SUBREGATOR_HISTORICAL_CHECKS` stay empty; the Routinator cache is operational validation state, not a new public history archive.

## Staged enablement and rollback

1. Record the backend digest, Compose configuration, current metrics, free memory, disk and inodes. Do not change PostgreSQL, frontend, existing IRRd or archive settings.
2. Validate `docker compose -f deploy/routinator/compose.yaml config --quiet`, then start that standalone project. Keep `SUBREGATOR_ROUTINATOR_URL` empty in the backend while initial synchronization runs.
3. Check `/api/v1/status` internally. Compare a bounded set of real IPv4/IPv6 and explicit prefix/ASN cases using `/validity?asn=...&prefix=...` with RIPEstat, including missing ROAs, ASN mismatch and length failures. Compare statuses and explanations, recording source times and genuine dataset differences. Do not require equal VRP ordering or claim synchronization implies universal completeness.
4. Add the external private network to the backend with `deploy/routinator/backend-network.yaml` as a Compose override, or copy that backend/network stanza into the deployed image-only Compose. Render and dry-run the exact deployment; retain existing default/edge networks and unrelated image digests. Set the URL and recreate only backend after its new image passes review and CI.
5. Verify health, cached REST/MCP and offer provenance, counters, queue ages, memory and persistence. Compare external request mix across an observation window and report remaining BGP-origin dependence. No database migration is required.
6. Roll back by clearing the URL and restoring the prior backend digest/configuration. The RIPEstat cache is retained; do not erase either cache volume or database. A source switch intentionally has no fresh local positive until the selected validator has been confirmed by collection.

Official sources and pinned manifest checked on 2026-11-27. Live pilot and production observations must be recorded separately from this implementation description.
